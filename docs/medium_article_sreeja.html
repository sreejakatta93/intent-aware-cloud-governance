Beyond CPU Thresholds: Using Intent-Fit Score to Detect Cloud Workload Misalignment

Why utilization metrics often measure symptoms rather than causes — and how intent-aware scoring changes what you can detect.

SK
Sreeja Katta Systems Researcher · PBCP Project

The alert never fired. The dashboard stayed green. The monitoring system reported CPU utilization at a healthy 71%, well above the underutilization threshold.

But something was wrong.

The workload had been submitted as a lightweight data validation job — expected to complete in 20 minutes on a small cluster. Six hours later it was still running, consuming 14 nodes, and had quietly accumulated over $200 in compute charges. The CPU number was technically accurate. The job was busy. It just wasn't doing what it was supposed to do.

Traditional monitoring had no way to know the difference. It was measuring how much the workload was using resources. It had no model of what the workload was supposed to be.

"What if utilization metrics are measuring symptoms — and the actual disease is something they were never designed to see?"

This question is the starting point for the work described here. It comes from PBCP — Pre-Billing Cost Prevention, a cloud governance research project I developed with Keerthi Rapolu. Keerthi led the pre-billing prevention architecture: the simulation engine, the Cost Prevention Score (CPS), the decision-theoretic intervention model, the runtime correction system, and the policy learning loop. My contribution focused on the measurement and intelligence layer: the Intent-Fit Score (IFS), the Intent-Behavior Divergence (IBD) framework, the anomaly detector, the root cause analyzer, and the prevention feedback loop that connects detected failures back to future policy.

This article is about that measurement layer — why it was needed, how it works, and what it reveals that CPU thresholds cannot.

01
The Limits of CPU-Based Monitoring

CPU utilization is a measure of busyness. It tells you how hard a processor is working. It does not tell you whether the work being done is the right work, at the right scale, for the right duration.

The dominant approach to cloud anomaly detection relies on thresholds applied to utilization metrics: if CPU drops below 20%, the workload is flagged as idle waste. If it stays above 60%, the system is considered healthy. This model has real value — it catches the obvious case where a cluster is running completely unloaded.

But it misses an entire category of failure.

The Threshold Blind Spot

A workload can show 65% CPU utilization, pass every monitoring check, and still be consuming 4× the resources it needs — simply because it was miscategorized, over-provisioned, or is running 8 hours past its expected completion time.

Consider three scenarios where CPU thresholds generate false confidence:

Scenario CPU Reading What's Actually Happening Threshold Alert?
Runaway ML job 68% (healthy) Training diverged, running 6× longer than declared No alert
Over-provisioned ETL 55% (acceptable) 20 nodes doing work that 6 could handle No alert
Mislabeled batch job 71% (healthy) Declared as "lightweight validation", behaving like ML training No alert

In each case, the resource is being used. The utilization number looks reasonable. The threshold model has no mechanism to ask: is this workload doing what it said it would do?

02
The Intent Gap

When a workload is submitted to a cloud scheduler, it carries a declaration — explicit or implicit — of what it intends to do. A job description like "nightly ETL transformation, 500GB source data, expected runtime 90 minutes" contains information that monitoring systems almost universally ignore. It gets logged, maybe, and then discarded.

The intent gap is the space between what a workload declares and what it actually does. It is not always a sign of malice or error — workloads diverge from their declared intent for many legitimate reasons: data volume changes, upstream schema shifts, model training that runs longer than expected, or resource requirements that weren't accurately known at submission time.

But the intent gap is also exactly where cloud waste hides.

Core Observation

Cloud waste is not primarily caused by idle resources. It is primarily caused by resources doing the wrong thing at the wrong scale for the wrong duration — all of which are invisible to utilization-only monitoring.

The key insight is that intent is measurable. If you embed a natural-language workload description into a vector space, and separately embed a representation of its observed runtime behavior, the cosine distance between those two vectors is a quantifiable measure of how well the workload kept its own promise.

That is the foundation of IFS.

03
Intent-Behavior Divergence

Intent-Behavior Divergence (IBD) is the formal framework for classifying workloads whose runtime behavior significantly departs from their declared intent. A workload is classified as exhibiting IBD when its Intent-Fit Score falls below a threshold — specifically, IFS < 0.65 in our benchmark.

IBD manifests in three primary patterns:

Type Mismatch

A workload declared as one class (e.g., batch) behaves at runtime like another class (e.g., ml_training). This is the most consequential divergence type because the two classes often have fundamentally different resource requirements, expected durations, and cost profiles. A scheduler that provisions for a batch job and gets ML training behavior will almost certainly produce waste or failure.

Resource Mismatch

The workload uses significantly more or fewer resources than its declared intent predicted. An over-provision factor of 2× or higher — requesting 20 nodes for work that uses 6 — is the single largest driver of avoidable cloud cost in our benchmark.

Duration Overrun

The workload runs substantially longer than its declared expected duration. A job that declares a 2-hour runtime and runs for 14 hours accumulates unbounded cost — often past any budget owner's monitoring window.

IBD is not a failure of the workload in isolation. It is a failure of the governance system to detect and respond to the divergence before the cost is incurred.

04
Introducing Intent-Fit Score (IFS)

IFS is defined as the cosine similarity between two embeddings: the intent embedding derived from the workload's natural-language description, and the behavior embedding derived from observed runtime telemetry.

IFS = cosine_similarity( embed(intent_description), embed(runtime_behavior) ) IFS ∈ [0, 1] · Higher values indicate stronger alignment between declared intent and observed behavior

For transparency and diagnostics, IFS is surfaced through four interpretable sub-scores that reflect the dimensions most relevant to cloud waste detection:

Type alignment weight: 0.35
Declared workload class vs. inferred class from runtime behavior
Utilization alignment weight: 0.25
Predicted CPU utilization vs. observed utilization
Duration alignment weight: 0.20
Expected job duration vs. actual completion time
Resource alignment weight: 0.20
Over-provision factor relative to declared resource requirements

05
Why Alignment Matters

The core claim of IFS is that workload alignment — not just utilization level — predicts cloud waste more accurately and more early. To understand why, consider what a high-IFS workload looks like versus a low-IFS one.

A workload with IFS of 0.96 submitted resources close to what it actually needed, ran roughly as long as it said it would, and behaved like the type of job it declared. Its cost was predictable. Its resource footprint was appropriate. Any governance system handling it well could do so with minimal intervention.

A workload with IFS of 0.41 is a different story. It may have high CPU utilization — the resource is being used — but the pattern of that use looks nothing like what the workload declared. It is running the wrong kind of computation, at the wrong scale, for much longer than planned. The cost it is accumulating was not anticipated. The governance system that approved its provisioning did so based on a description that turned out to be inaccurate.

The Alignment Principle

Misaligned workloads are not just waste events. They are governance failures — cases where the system approved a resource request based on declared intent, and the actual behavior made that approval incorrect in retrospect.

This reframing matters because it changes what governance needs to measure. A system that only measures utilization will catch idle resources. A system that measures alignment will catch workloads that are actively using resources for the wrong purpose — which is where the larger and more consequential waste lives.

06
Detecting Anomalies Earlier

With IFS defined, the anomaly detection problem becomes a classification task: given a workload's IFS trajectory over time, predict whether it is exhibiting IBD.

The IFS-based detector was compared against a CPU-threshold baseline — the standard approach used in most cloud monitoring tools — on a benchmark of 500 workloads with controlled anomaly injection.

The recall improvement was larger than the precision improvement. This is the important number. Recall measures the fraction of actual anomalies that the detector correctly identifies — and the IFS-based detector catches significantly more of them than a threshold approach.

The reason is structural. CPU thresholds can only flag anomalies that manifest as utilization outliers. A workload that maintains moderate CPU while running 6 hours past its expected completion will not trigger a CPU alert. Its IFS, however, will begin degrading from the first hour of overrun as the duration sub-score pulls the alignment score down. The signal is available earlier, and it does not require the anomaly to express itself in a single metric channel.

Benchmark Note

These results are from a controlled synthetic benchmark with calibrated anomaly injection. The absolute numbers are illustrative; the directional signal — that semantic alignment improves detection over single-metric thresholding — is the finding that should be generalized.

07
Root Cause Analysis

Detecting that a workload has diverged is necessary but not sufficient for actionable governance. Knowing why it diverged is what makes the detection useful.

The Root Cause Analyzer (RCA) takes a flagged IBD workload and attributes the divergence to one or more root cause categories using the IFS sub-score decomposition. Because each sub-score corresponds to a measurable dimension of alignment — type, utilization, duration, resource — the sub-score that contributes most to the IFS drop identifies the most likely root cause.

Root Cause Driving Sub-Score Governance Implication
Type mismatch Type alignment drop Workload was submitted under the wrong class; provisioning policy was wrong from the start
Over-provisioning Resource alignment drop Node count was excessive for actual utilization; right-sizing would have prevented waste
Duration overrun Duration alignment drop Job ran far beyond declared time; runtime termination policy should have triggered earlier

The output of RCA is not just a classification — it is an explanation in plain language that can be surfaced to the team responsible for the workload. Instead of "this job was flagged as anomalous," the system can say: "this job was submitted as a batch workload but exhibited ML training behavior, which caused it to run 4× longer than its declared duration at a resource footprint 3× what was needed."

That is a governance event that can be acted on. The generic alert cannot.

Prevention Feedback Loops

Detection and RCA produce value on their own. But the more significant contribution of the IBD framework is what happens next: low-IFS workloads feed a prevention feedback loop that improves future governance decisions.

The key component is the AnomalyPreventionFeedback module, which watches for recurring IBD patterns. When the same anomaly signature appears three or more times with sufficient confidence (≥ 0.60), the system synthesizes a new prevention rule and adds it to the governance layer. The next workload that matches the pattern is intercepted before the waste occurs — not after.

09
How Low-IFS Workloads Improve Future Policies

There is a counterintuitive property of this system worth naming explicitly: low-IFS workloads are not just problems — they are information.

Every workload that diverges from its declared intent and triggers an IBD event contributes a labeled training example: this description, this submission pattern, this resource request produced this behavior. If that pattern recurs, the system now has evidence that the declared intent is systematically misleading for this class of workload.

This is how the intelligence layer connects to Keerthi's policy learning loop. The IBD events I track become the signal that drives Phase 3 convergence — the system learns not just from successful interventions, but from every case where alignment broke down and the governance system had to respond.

The Learning Connection

IFS turns failed workloads into governance training data. Each misalignment event that is correctly diagnosed makes the system harder to fool by the same pattern in the future.

The embedding updates that happen after each IBD event also refine the FAISS retrieval index. Future workloads that describe themselves similarly to past divergers are retrieved with higher suspicion scores — their prior distributions are updated to reflect the known tendency for that description pattern to produce misaligned behavior.

On the detection result

The F1 improvement from 0.6054 to 0.7608 is meaningful but not dramatic. The more important number is the recall improvement: IFS-based detection catches substantially more actual anomalies than a threshold approach. In governance systems, missing a real anomaly (false negative) is generally more expensive than flagging a healthy workload for review (false positive). Higher recall matters.

On the learning result

The 56× improvement in peak CPS between Full PBCP and the No-Phase-3 baseline is the most striking number in the evaluation. It is not a result of better simulation or smarter thresholds — it is a result of the feedback loop connecting IBD events to policy updates. Static rules contribute little. Retrieval alone is useful. The combination of alignment tracking, anomaly detection, and policy synthesis is what produces the large separation.

11
Lessons Learned

A few things became clearer over the course of building and evaluating this system:

Intent is a richer signal than it appears. A natural-language job description contains information that is regularly discarded by scheduler systems. Encoding that description and comparing it to runtime behavior is a surprisingly effective diagnostic, even with a relatively simple embedding approach.

Sub-scores matter more than the aggregate. The composite IFS is useful for ranking workloads by alignment quality. But for RCA and for building governance policies, the sub-score decomposition is what makes the system actionable. A score of 0.50 caused by type mismatch requires a different response than a score of 0.50 caused by duration overrun.

Detection without action is incomplete. The IBD framework only becomes valuable when it is wired to the prevention feedback loop. An anomaly that is detected, labeled, and then forgotten is an opportunity cost. The same anomaly that seeds a prevention rule is a system improvement.

The boundary between measurement and prevention is artificial. The clearest lesson from this project is that governance quality is determined by what happens at the interface between the measurement layer and the prevention layer — not by optimizing either in isolation.

12
Future Directions

Several directions would meaningfully strengthen this work:

Real-trace calibration. The benchmark uses synthetic workloads calibrated against published cloud pricing. Running the IFS framework against actual organizational telemetry would validate whether the detection improvements hold under real behavioral distributions.

Stronger baselines. The CPU-threshold baseline is the most common approach in practice, but it is not the strongest possible baseline. Comparing against a statistical anomaly detector (e.g., isolation forest on telemetry features) would produce a more conservative estimate of IFS's contribution.

Streaming IFS. The current implementation computes IFS post-execution. An incremental IFS that updates as telemetry arrives — providing an alignment signal while a job is still running — would enable earlier runtime intervention.

Cross-organizational transfer. Policy rules synthesized from one organization's IBD patterns may partially generalize to others with similar workload profiles. Whether learned policies transfer is an open empirical question.
